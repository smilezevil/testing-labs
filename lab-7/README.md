# Лабораторна робота №7 — Performance and Load Testing (JMeter + k6)

SUT: SUT B «Прокат обладнання», варіант 04 — REST API з папки `../lab-6` (код застосунку без змін).

## Сценарій

Кожен віртуальний користувач (VU) по колу виконує:

1. `POST /rentals` — оформлення оренди, очікується 201; з відповіді береться `id`.
2. `GET /rentals/{id}` — читання оренди за `id` з попереднього кроку, очікується 200 і `status = Active`.
3. `POST /rentals/{id}/return` — повернення, очікується 200 і `status = Returned`.
4. Пауза 0.5 с (think time).

Перед тестом один раз створюється обладнання (`POST /equipment`); його `id` використовується в усіх орендах.
Якщо оренду не створено, наступні запити ітерації не надсилаються.

| | k6 (`k6/rental-scenario.js`) | JMeter (`jmeter/rental-scenario.jmx`) |
|---|---|---|
| Створення обладнання | `setup()` | setUp Thread Group + JSR223 PostProcessor (`props`) |
| Передача id оренди | `created.json('id')` → змінна `rentalId` | JSON Extractor `$.id` → `${rentalId}` |
| Перевірки | `check()` | Response Assertion (код) + JSON Assertion (`$.status`) |
| Think time | `sleep(0.5)` | Constant Timer 500 ms |
| Унікальний `reference` | `K6-<час>-<VU>-<ітерація>` | `JM-${__UUID()}` |

## Workload profile

| Профіль | VU | Ramp-up | Утримання | Разом |
|---|---|---|---|---|
| baseline | 2 | 5 с | 55 с | 60 с |
| load | 20 | 15 с | 75 с | 90 с |
| stress | 100 | 30 с | 60 с | 90 с |

k6: executor `ramping-vus` з двома stages. JMeter: Thread Group (Number of Threads, Ramp-up, Duration = ramp-up + утримання).

## Thresholds (визначені до запусків)

- p95 часу відповіді < 500 мс;
- error rate < 1 %;
- k6 додатково: успішних checks > 99 %.

k6 перевіряє їх сам (за порушення — код виходу 99). Для JMeter ті самі межі перевіряє `scripts/metrics.py` за `statistics.json` з HTML-звіту.

Середовище: Mac з Apple Silicon; SUT (Spring Boot, Java 25), PostgreSQL 17 у Docker і генератор навантаження працюють на одному комп'ютері. k6 v2.3.0, JMeter 5.6.3. Запуски 21.10.2026, папки в `results/`.

## Висновки

1. **Throughput росте пропорційно кількості користувачів**: 10.7 → 106 → 480 req/s (×10 і ще ×4.5). Один VU робить приблизно 1.6–1.8 сценарію за секунду, що близько до теоретичної межі 1 / (0.5 с паузи + час трьох запитів). Отже, навіть при 100 VU інтенсивність обмежена паузою користувача, а не сервером — SUT встигає обробляти все навантаження.
2. **Average майже не змінюється (5–8 мс), а p95 росте під stress**: k6 11.7 → 19.3 мс, JMeter 17 → 30 мс; p95 для GET і return зріс у 2–4 рази (4–7 → 15–16 мс). Це перші ознаки черг: 100 одночасних користувачів ділять пул з'єднань з БД (10 за замовчуванням) і процесор, на якому ще працюють Docker і генератор. Середнє цього майже не показує, бо більшість запитів так само швидкі — тому важливо дивитись саме p95.
3. **Baseline трохи повільніший за load** (k6 avg 7.6 проти 4.9 мс, поодинокий max 285 мс): baseline запускався першим одразу після старту застосунку, коли JVM ще «прогрівалась» (JIT-компіляція, ініціалізація пулу з'єднань). Це варто враховувати: перші секунди після старту не показові.
4. **POST /rentals — найповільніша операція** на всіх профілях: це транзакція з читанням обладнання і двома INSERT, тоді як GET — один SELECT.
5. **Помилок немає (0 %), усі thresholds виконані з великим запасом** (p95 ≤ 30 мс при межі 500 мс). Межу стійкості системи stress-тест не знайшов: при 100 VU SUT працює стабільно. Для пошуку межі потрібне більше навантаження або генератор на окремій машині.

### Порівняння k6 і JMeter

- **Однаковий workload підтверджений результатами**: кількість запитів і throughput у load і stress відрізняються приблизно на 1 % (160.0 проти 160.3 сценаріїв/с у stress), у короткому baseline — до 5 %.
- **Час відповіді в JMeter дещо вищий** (p95 у stress 30 проти 19 мс). Причини: JMeter заокруглює час до цілих мілісекунд і рахує в ньому весь цикл запиту, а `http_req_duration` у k6 не включає встановлення з'єднання; крім того, JMeter запускає кожного користувача як окремий Java-потік і сам навантажує процесор сильніше, ніж k6, а генератор і SUT ділять один комп'ютер.
- **Error rate рахується по-різному**: у JMeter у відсоток помилок входять і провалені assertions, у k6 `http_req_failed` — лише HTTP-помилки, а логічні перевірки йдуть окремо в `checks`.
- **Особливості інструментів**: k6 — сценарій як JavaScript-код, thresholds вбудовані (k6 сам позначає запуск як неуспішний), легкий за ресурсами, вбудований HTML-звіт. JMeter — сценарій як дерево елементів (`.jmx`, зручно в GUI), багато готових компонентів (extractor, assertions, timers), докладний HTML-dashboard, але агрегованих thresholds «з коробки» немає — їх тут перевіряє `scripts/metrics.py`.

### Обмеження експерименту

Генератор, SUT і БД працюють на одному комп'ютері й конкурують за ресурси; БД між запусками не очищалась (кількість оренд росла); абсолютні значення залежать від обладнання і на іншому комп'ютері будуть іншими.
